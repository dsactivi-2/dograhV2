## Overview

Dograh exposes an [MCP (Model Context Protocol)](https://modelcontextprotocol.io/) server that lets AI assistants like Codex, Claude Code, Claude Desktop, and Cursor access your workspace and documentation. Once connected, an assistant can list your agents, fetch agent definitions, and search Dograh docs on your behalf.

## Prerequisites

- Credentials (pick one — see [Authentication](#authentication) below):
  - **Access token (recommended for agents)** — short-lived; no permanent API key required
  - **API key** — long-lived organization key
- Your Dograh MCP endpoint:
  - Hosted: `https://app.dograh.com/api/v1/mcp/`
  - Self-hosted: `<YOUR_BACKEND_URL>/api/v1/mcp/`

The endpoint is also shown in **Platform Settings → MCP Server** inside the Dograh UI.

<Note>
If you deployed Dograh to a remote server using [`setup_remote.sh`](/deployment/docker#option-2%3A-remote-server-deployment), your endpoint is served with a self-signed SSL certificate. Claude Code will refuse MCP connections to it unless you start the CLI with TLS verification disabled:

```bash
NODE_TLS_REJECT_UNAUTHORIZED=0 claude
```

This is only required for self-signed certificates. If you have set up a [custom domain](/deployment/custom-domain) with Let's Encrypt certificates via Certbot, no extra flag is needed.
</Note>

## Authentication

The MCP endpoint reuses the same auth stack as the REST API. Send credentials on every request (Streamable HTTP and SSE).

| Method | Header | When to use |
|---|---|---|
| Access token | `Authorization: Bearer <token>` | Preferred for coding agents — no permanent API key |
| API key | `X-API-Key: <key>` or `Authorization: Bearer dgr_...` | Scripts, CI, long-lived agent configs |

### Option A — Access token (no permanent API key)

#### Self-hosted / local auth (`AUTH_PROVIDER=local`)

Log in (or sign up) against your backend to mint a short-lived JWT, then pass it as a Bearer token:

```bash
# Obtain a JWT (valid for OSS_JWT_EXPIRY_HOURS, default 24h)
curl -s -X POST https://your-dograh-instance/api/v1/auth/login \
  -H "Content-Type: application/json" \
  -d '{"email":"you@example.com","password":"your-password"}'
# → { "token": "<jwt>", "user": { ... } }
```

Use the returned `token` in MCP client configs:

```text
Authorization: Bearer <jwt>
```

#### Hosted / Stack Auth (`AUTH_PROVIDER=stack`)

Pass a valid **Stack Auth access token** in the Authorization header. This is the same short-lived session token the Dograh web app uses for REST calls:

```text
Authorization: Bearer <stack_access_token>
```

How to obtain a Stack Auth access token:

1. Sign in to the Dograh dashboard in your browser.
2. Open DevTools → Application / Network and copy the access token from an authenticated API request’s `Authorization` header, **or**
3. Use the Stack Auth client SDK / session API for your project to mint a fresh access token programmatically.

The token is validated server-side via Stack Auth (`/api/v1/users/me`). When it expires, refresh or re-login and update the MCP client header.

<Note>
Access tokens are short-lived by design. Prefer them over permanent API keys for interactive agent use. Do not commit tokens to source control.
</Note>

### Option B — API key (legacy / long-lived)

Generate a key at [`/api-keys`](https://app.dograh.com/api-keys) (or `http://localhost:3010/api-keys` for self-hosted). See [API Keys](/configurations/api-keys).

```text
X-API-Key: dgr_...
# or, equivalent:
Authorization: Bearer dgr_...
```

API keys start with `dgr_`. When a Bearer value has that prefix, the MCP server treats it as an API key (not a JWT/Stack token) so existing clients keep working.

## Claude Code

### With an access token

```bash
claude mcp add --transport http dograh https://app.dograh.com/api/v1/mcp/ \
  --header "Authorization: Bearer YOUR_ACCESS_TOKEN"
```

### With an API key

```bash
claude mcp add --transport http dograh https://app.dograh.com/api/v1/mcp/ \
  --header "X-API-Key: YOUR_API_KEY"
```

Replace `YOUR_ACCESS_TOKEN` / `YOUR_API_KEY` with the credential you obtained. For self-hosted deployments, swap the URL for your backend.

Verify the server is connected:

```bash
claude mcp list
```

## Codex

Open Codex's config file (`~/.codex/config.toml`) and add a `dograh` MCP server.

### With an access token

```toml
[mcp_servers.dograh]
url = "https://app.dograh.com/api/v1/mcp/"
http_headers = { "Authorization" = "Bearer YOUR_ACCESS_TOKEN" }
```

### With an API key

```toml
[mcp_servers.dograh]
url = "https://app.dograh.com/api/v1/mcp/"
http_headers = { "X-API-Key" = "YOUR_API_KEY" }
```

If you prefer to keep the credential out of `config.toml`, store it in an environment variable instead:

```toml
[mcp_servers.dograh]
url = "https://app.dograh.com/api/v1/mcp/"
env_http_headers = { "Authorization" = "DOGRAH_ACCESS_TOKEN" }
# or: env_http_headers = { "X-API-Key" = "DOGRAH_API_KEY" }
```

Then set the variable before starting Codex:

```bash
export DOGRAH_ACCESS_TOKEN="YOUR_ACCESS_TOKEN"
# or: export DOGRAH_API_KEY="YOUR_API_KEY"
codex
```

Verify the server is registered:

```bash
codex mcp list
codex mcp get dograh
```

## Claude Desktop

Open Claude Desktop's config file (`claude_desktop_config.json`) and add the `dograh` entry under `mcpServers`:

### With an access token

```json
{
  "mcpServers": {
    "dograh": {
      "url": "https://app.dograh.com/api/v1/mcp/",
      "headers": {
        "Authorization": "Bearer YOUR_ACCESS_TOKEN"
      }
    }
  }
}
```

### With an API key

```json
{
  "mcpServers": {
    "dograh": {
      "url": "https://app.dograh.com/api/v1/mcp/",
      "headers": {
        "X-API-Key": "YOUR_API_KEY"
      }
    }
  }
}
```

Restart Claude Desktop after saving. The Dograh tools should appear in the tool picker.

## Cursor and other MCP clients

Any MCP client that supports Streamable HTTP transport can connect with the same URL and headers.

**Cursor** (`~/.cursor/mcp.json` or project `.cursor/mcp.json`):

```json
{
  "mcpServers": {
    "dograh": {
      "url": "https://app.dograh.com/api/v1/mcp/",
      "headers": {
        "Authorization": "Bearer YOUR_ACCESS_TOKEN"
      }
    }
  }
}
```

**Generic** (any Streamable HTTP client):

| Field | Value |
|---|---|
| Transport | Streamable HTTP |
| URL | `https://app.dograh.com/api/v1/mcp/` (or your self-hosted URL) |
| Auth header | `Authorization: Bearer <token>` **or** `X-API-Key: dgr_...` |

## Example prompts

Once the MCP server is connected, you can drive Dograh from your coding agent in plain English. A few prompts to try:

**Explore your workspace**

- "List my agents in Dograh."
- "Show me the definition of the agent called *Lead Qualifier*."
- "Which credentials and tools are configured in my Dograh workspace?"
- "List the recordings from my most recent agent."

**Edit an agent**

- "In my *Lead Qualifier* agent, add a new agent node after the greeting that asks the caller for their budget, then routes to the existing qualification node."
- "Add an end-call node to *Support Bot* that triggers when the user says they are done, with a polite goodbye prompt."
- "Rename the *intro* node in *Lead Qualifier* to *greeting* and update any edges that reference it."
- "Change the LLM model on all agent nodes in *Support Bot* to `gpt-4o-mini`."

**Learn the platform**

- "Search the Dograh docs for how to configure a TURN server."
- "What node types does Dograh support, and what fields does a `knowledge_base` node take?"
- "How do I deploy Dograh on a custom domain with HTTPS?"

<Note>
Agent edits are saved as a new **draft** version — your published agent keeps serving calls until you explicitly publish the draft from the Dograh UI.
</Note>

<Note>
Credentials control which workspace the assistant sees. Treat access tokens and API keys like any other secret — do not commit them to source control or paste them into shared chats.
</Note>

## Migration notes

- **Existing API-key MCP configs keep working** with no changes (`X-API-Key` and `Authorization: Bearer dgr_...`).
- To drop permanent API keys, switch the header to `Authorization: Bearer <access_token>` as described above.
- No new environment variables are required for this auth path. Token lifetime for local JWTs is still controlled by `OSS_JWT_EXPIRY_HOURS`; Stack Auth token lifetime is controlled by your Stack Auth project settings.
